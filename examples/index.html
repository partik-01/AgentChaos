The project behind the walkthrough

Five parts, one independent answer.

The agent’s reply and the payment ledger are different sources of information. Agent Chaos records both, then checks the outcome independently.

01 / Target agent

Decides what to do

The support agent reads the request, calls payment tools, handles errors, and replies to the customer. You can test the flawed or corrected scripted policy, or the optional OpenAI adapter.

02 / Payment service

Tracks the actual money

SQLite stores simulated payments and refunds. It checks ownership and the remaining balance. Repeating an identical request with the same idempotency key returns the original refund.

03 / Fault middleware

Changes what the agent sees

A scenario can fail a call before execution, hide a successful response, delay visibility, return malformed data, or rate limit a call. The underlying ledger remains separate.

04 / Outcome verifier

Checks the business result

It reads authoritative state to check the customer, payment, amount, balance, duplicate effects, and unrelated payments. Completion claims also need observed confirmation.

05 / Recorder and runner

Keeps the evidence

Each trial gets its own database. Messages, tool calls, faults, ledger events, configuration, and final results are saved as JSON and a readable HTML report.

Run the project

You can test this without an API key.

After following the README quick start and activating the Python environment, run these from the project folder. The first command intentionally fails to expose the duplicate refund.

Expose the timeout failure
agent-chaos run scenarios/03_after_timeout.yaml --agent flawed
Rerun saved evidence with the corrected agent
agent-chaos rerun examples/timeout-flawed.json --agent corrected
Compare both policies over repeated trials
agent-chaos compare scenarios --trials 5

Playback, reruns, and uncertainty

Playback reads an existing trace without calling tools or a model. A rerun restores the recorded initial database and executes the agent again. A seed reproduces fault scheduling, but cannot make a live model deterministic.

A financial or claim violation is an agent failure. A broken execution is a harness error. Unverified completion or unassessed model prose is inconclusive when financial checks otherwise succeed. Neither errors nor inconclusive runs count as passes.
